## Design

A trip is an **event of kind `bus`**, so approval, bookings, check-in, payouts, cancel + refund and the
admin pages all work unchanged. Extra bits:

- `bus_trips` (one row per trip event): origin, destination, duration (minutes), coach type
  (`seater` 2+2, `vip` 2+1, `sleeper` 1+1), amenities. Boarding point = the event's `venue`; boarding
  address = the event page's `venue_detail`; the trip's description = the event page's `about`.
- One ticket type, **"Seat"**, price = the merchant's price, quantity = the coach's seat count. Sold, left,
  revenue, commission and payouts then work as for any event.
- `booking_seats` (booking, event, seat id, passenger gender, held): a seat is held by at most one live
  booking (unique index on held rows); cancelling a booking releases its seats. Taken seats show the
  passenger's gender (female / male) to other buyers, as the user app's design does; door-sold seats show
  as plain taken.
- Seat maps are generated from the coach type (same shape as the user app's mock: ids `1A`..., 2+2 has 10
  rows of A B _ C D, VIP 2+1 10 rows of A _ B C, sleeper 1+1 8 rows of A _ B).
- Buyers choose seats (max 8 per booking); the server checks they exist, are free, and holds them while it
  holds the event row (no double sale). Door sales for a trip get the next free seats automatically.

API (all new except where said):

- Merchant: `POST /merchant/events/bus-trips` (owner of a Bus business) {origin, destination, startsAt,
  durationMinutes, coachType, priceCents, boardingPoint, boardingAddress?, about?, amenities?} -> the
  event JSON. Merchant event and booking JSON gain `bus` / `seats`. `POST /merchant/events` is refused for
  Bus businesses and kind `bus` there.
- Buyer: `GET /catalog/bus/routes` (routes of trips on sale), `GET /catalog/bus/departures?origin=&destination=&date=`,
  `GET /catalog/bus/departures/{id}/seats`; `POST /buyer/bookings` takes `seats` (ids) instead of `lines` for
  a trip. Buyer booking JSON gains `seats` and the event's `bus` details.
